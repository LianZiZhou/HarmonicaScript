## The seam

```csharp
public interface IClock { long Frequency { get; } long GetTimestamp(); void WaitUntil(long target); }
public interface IInputBackend : IDisposable {
    string Id { get; }
    void Emit(ReadOnlySpan<CompiledEvent> batch);   // every event in the span shares one deadline
    void ReleaseAll(ReleaseReason reason); }
public interface IEnvironmentProbe { EnvironmentFacts Read(); }   // RAW FACTS ONLY, no policy
internal interface ISendInputApi { uint SendInput(ReadOnlySpan<INPUT> inputs); }
public readonly record struct CompiledEvent(long DeadlineTicks, ushort Code, bool IsDown, bool IsMouse);
```

Four backends — `WindowsSendInputBackend` (production), `MacCgEventBackend` (dev/loopback), `TraceBackend` (the test *is* the transcript), `FaultInjectingBackend` (wraps another, aborts at event N in six modes). Two clocks — `StopwatchClock` and `VirtualClock` (`WaitUntil` sets `_now = target`; a 3-minute song runs in microseconds).

`VirtualClock` + `TraceBackend` makes the **entire** playback engine deterministically testable on macOS: countdown, release-all-at-start, focus guard, panic hotkey, pause/resume, seek, mid-song speed change, exception paths, signal paths.

## Compile, validate, then run

`CompiledSchedule.Compile(timeline, profile, clock, t0)` converts `TimeMs → t0 + TimeMs × Frequency / 1000` **exactly once**; sub-millisecond precision lives in the wait, never in the IR. Seek is a binary search on a sorted array; speed change and live re-transposition are a full recompile (single-digit ms); pause is stop + `ReleaseAll` + reseek. `TimelineValidator` runs unconditionally before the countdown — **a timeline that fails validation is never injected**.

Scheduler: one dedicated non-background `Thread { Priority = Highest, Name = "HarmonicaScheduler" }`; absolute deadlines against `Stopwatch`, never `Sleep(delta)`; `CreateWaitableTimerEx(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION = 0x2, TIMER_ALL_ACCESS = 0x1F0003)` + `SetWaitableTimer` with a negative 100 ns due time down to ~1.5 ms remaining, then a `Thread.SpinWait` tail; `timeBeginPeriod(1)`/`timeEndPeriod(1)` (per-process since Win10 2004, so we must call it); `AvSetMmThreadCharacteristicsW("Pro Audio", ref taskIndex)` with `taskIndex = 0` on first call, degrading silently on `ERROR_INVALID_TASK_NAME`; `ProcessPriorityClass.High`, never `RealTime`; `GCLatencyMode.SustainedLowLatency` restored in `finally`; allocation-free hot loop; a warm-up pass against `TraceBackend` before the countdown so JIT and P/Invoke stubs resolve.

## SendInput specifics

`INPUT_KEYBOARD (1)`, `ki.wVk = 0`, `ki.wScan = ScanCode1` from `keytable.json`, `dwFlags = KEYEVENTF_SCANCODE (0x0008)` on key-down and **`0x000A` (`SCANCODE | KEYUP`) on key-up** — omitting SCANCODE on key-up is the single most common cause of stuck notes in this class of tool and it is a one-line test. `KEYEVENTF_EXTENDEDKEY` where the Set-1 code carries the E0 prefix (none of our eight do: `0x2C 0x2D 0x2E 0x2F 0x30 0x31 0x32 0x33`). Mouse: `MOUSEEVENTF_LEFTDOWN/UP 0x0002/0x0004`, `RIGHTDOWN/UP 0x0008/0x0010`, `MIDDLEDOWN/UP 0x0020/0x0040`, `dx = dy = mouseData = 0`, and **never `MOUSEEVENTF_MOVE`** — the cursor and camera must not move. `stackalloc INPUT[n]`, always pass `sizeof(INPUT)` (40 bytes x64). All events sharing a `TimeMs` go in **one** `SendInput` call, which is what makes modifier-arm + note-strike atomic (MSDN guarantees non-interspersal). Signatures generated by CsWin32, never hand-typed. VK-only injection is not used at all: many games reading DirectInput or raw input ignore it.

Hotkeys via `RegisterHotKey(NULL, id, MOD_NOREPEAT|…, vk)` on a dedicated message-pump thread — **never** `SetWindowsHookEx(WH_KEYBOARD_LL)`, which is the API anti-cheats watch hardest. F6 = start/pause/resume/cancel (matching the incumbent, so his users' muscle memory transfers), F7 = panic release-all. Never bare Esc (in-game menu key, and `RegisterHotKey` swallows it), never F12 (debugger-reserved).

## Stuck-key safety — layered, and honest about each layer

A stuck held **mouse** button in an online FPS is continuous fire and is the worst thing this project can produce.

1. **Hold caps are a compile-time property of the `InputTimeline`, not a scheduler behaviour.** `emit.holdCaps` splits any key hold > `maxKeyHoldMs` (4000) into a re-press with a `noteGapMinMs` gap flagged `HoldSplit`, and breaks any modifier run > `maxModifierHoldMs` (6000) at a rest of at least `exclusiveSwapMs`. If no qualifying rest exists in the window it splits at the least-bad point **and also splits the sounding note**, so the simulator's constant-pitch assertion still holds (the judge's "P19 provably breaks M4" flaw). Because the cap is a property of a serialised artefact, it is validated, golden-filed and simulated on a Mac — and it holds identically for an exported macro we do not control at runtime.
   *This replaces the winning plan's 300 ms scheduler-level re-press cap, which mutated the stream below the validator, was untested by construction, contradicted the plan's own "an all-sharp piece is one press and one release" costing, and did not bound anything after a hard kill.*
2. `try/finally` around the scheduler loop; `AppDomain.UnhandledException`; `PosixSignalRegistration` (SIGINT/SIGTERM/SIGQUIT); `Console.CancelKeyPress`; `ProcessExit`.
3. **A release-all batch at session START**, plus a `GetAsyncKeyState` sweep — this, not a hold cap, is the real recovery from a previous hard crash, and the docs say so plainly (MSDN: `SendInput` does not reset keyboard state).
4. `hsc watchdog --parent <pid> --state <path>`: an out-of-process watchdog that emits release-all for the recorded held set when the parent dies. Default on for live sessions, with its own trace goldens and its own fault-injection cases.
5. `TimelineValidator` refuses to play anything with an unpaired Down. The two exclusion-group members are **never** simultaneously down by construction, asserted at the *logical state* level (see below).

## The validator — a logical state machine, not event bookkeeping

The winning plan's invariant list was hold-shaped: pairing, no double-Down, nothing held at end, exclusivity, min-hold, min-gap, sortedness. Under **toggle** lowering a "press" is a click (down+up), so a timeline that leaves 半音 *latched on in-game* satisfies every one of those and passes green — exactly the failure the hold/toggle hedge exists to cover. So `TimelineValidator` replays the lowering's own semantics and asserts on the **logical** state:

- terminal logical state == Neutral (nothing latched, nothing held);
- exclusion-group members never simultaneously *active*;
- concurrent active modifiers ≤ `MaxSimultaneousModifiers`;
- **for every `NoteDown` at T requiring modifier set M, each `m ∈ M` became active at ≤ `T − m.PressLeadMs` and stays active through `T + ε`** — the lead-time invariant the winning plan omitted, which let a timeline arm a modifier at the identical `TimeMs` as the strike and still round-trip green;
- active-span durations within `maxKeyHoldMs` / `maxModifierHoldMs`;
- adjacent events for one code ≥ `minEventSeparationMs`;
- `(TimeMs, Phase, Device, Code)` unique and sorted; `Phase ∈ {NoteDown, ModifierDown} ⟺ IsDown`;
- every audible `ScoreNote` has exactly one `NoteDown`/`NoteUp` pair referencing its `Id`.

## Diagnosis of "nothing happened" — six rungs, with a test seam

The winning plan's ladder was good but was Windows-only code with no injectable seam, so the one piece of user-facing decision logic could not be unit-tested. Here `IEnvironmentProbe` returns **raw facts** (`EnvironmentFacts { ForegroundHwnd, GameHwnd, GamePid, OurIntegrityLevel, IsElevated, Hkl, NotificationState, WindowStyle, MonitorBounds, NotepadDeliveryResult }`) and `PreflightRules` is a **pure function** from facts → verdicts, driven by `data/diagnostics/rules.json` and golden-filed on the Mac across synthetic fact sets.

| # | Cause | Detection | Status |
|---|---|---|---|
| 1 | Game not focused | `GetForegroundWindow()` vs the game HWND from `EnumWindows` + `GetWindowThreadProcessId` matched against `GameProfile.ProcessNames`. Re-checked **before every batch** (a few hundred ns) | Solved. Also prevents typing `zxcvbnm` into Discord for four minutes |
| 2 | Exclusive fullscreen | `SHQueryUserNotificationState() == QUNS_RUNNING_D3D_FULL_SCREEN (3)` — documented, non-invasive, needs no process handle | Detected. Remedy: 切换到无边框窗口 |
| 3 | Wrong IME | `GetKeyboardLayout(GetWindowThreadProcessId(fgHwnd))`, LOWORD == 0x0804 → warn. Conversion *mode* is not observable from outside, but garbled Notepad readback exposes it | Layout detected; mode caught by rung 0 |
| 4 | UIPI / elevation | Our own elevation via `WindowsPrincipal.IsInRole(Administrator)`. **We deliberately do NOT `OpenProcess` the game** to read its integrity level — that is the one cross-process behaviour ACE advertises intercepting, and the information gain does not justify it | Not directly detectable. Offer 「以管理员身份重启」 (runas) **only from inside the wizard, never at startup, never by manifest** |
| 5 | In-game rebind / instrument not equipped / wrong game mode | Not observable at all. Mitigated by a **binding-capture UI**: a focused control in *our* window, 「请按下你的 1(do) 键」, read from Avalonia's `KeyEventArgs.PhysicalKey` → scan code. Layout-independent, no hooks, no game process | Not detectable; made trivially fixable |
| 6 | **All five green and still nothing** | The project-killing case: SendInput reaches Windows but the game filters `LLKHF_INJECTED` or does raw-input source checking | Stated as itself, with a one-click diagnostic bundle. Never reported as a generic failure |

**Rung 0 — the Notepad delivery test**, and its routing corrected. Launch `notepad.exe`, play a nonce built from the eight harmonica keys at the active profile's floors, `Ctrl+A`/`Ctrl+C`, read and restore the clipboard, diff. It proves the whole engine reaches a **real foreign process at our own integrity level**, proves the scan-code path, and exposes an active IME conversion mode immediately as garbled readback. The judge's correction is respected verbatim: **a green Notepad test does NOT clear rung 4**, because Notepad is medium-integrity — if the game runs elevated the test passes and the elevation cause is still live. The rules therefore keep rung 4 as *unresolved* on a green rung 0 and say so in the message. `--find-floor` (binary-searching `noteHoldMinMs` against readback) is **cut**: Windows imposes no meaningful minimum hold for a down/up pair to produce a character, so it would bottom out near 1 ms and write `measured: true` into the very field whose honesty badge is the point.

## The trace log = the golden file

**One canonical `TraceWriter`** produces both the `*.verified.trace` files in CI and the production run log. The event column carries the **scheduled** time (so goldens and production runs are diffable by construction); realised lateness is confined to the summary line; the header's env fields are normalised out by a documented canonicalisation rule.

```
# harmonicascript trace v1
# timeline=sha256:ab12cd… instrument=df.harmonica.v1@1 timing=df.reference@1 speed=1.000 backend=win-sendinput
     0.000  BATCH n=1
     0.000    DOWN mouse right                    note=-1  mod=octaveUp
    12.000  BATCH n=1
    12.000    DOWN key   0x2C Z hid=29            note=0   deg=1 state=+12 pitch=72
   192.000    UP   key   0x2C Z hid=29            note=0
187430.000  RELEASEALL reason=EndOfSong released=0
# summary events=1842 batches=1103 maxConcurrentHeld=2 stuckAtEnd=0 maxLateMs=0.7
```

`hsc diag` builds `hs-diag-<ts>.zip` locally (`report.json`, `env.txt`, effective profiles with per-field origin, `timeline.trace.txt`, hashes, `play.log`, rung answers, redaction report; the `.mid` only with explicit consent) and **opens the folder — it never uploads**. Then `hsc replay hs-diag-….zip --backend trace` re-runs the user's exact settings and profile snapshots on the developer's Mac and diffs the resulting trace against theirs. Traces match ⇒ the engine is right and the environment is wrong. That is the whole remote-debugging story, and it needs no network and no Windows machine.
